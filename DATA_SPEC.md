# Data collection specification — next-generation strategy research

**Purpose.** Stop optimising historical candle-touch backtests. Collect the
data required to estimate the value of a real passive order *before it is
submitted*, and optimise the execution policy directly.

Everything in this repo up to now models execution with assumptions — price
touches counted as fills, global winner/loser fill rates, displayed size used
as a proxy for queue. Those assumptions are the largest remaining source of
error. This document specifies what replaces them.

---

## 0. What the exchange actually provides — read this first

Three of the requirements below are constrained by what Kalshi exposes. Verified
against the live API on 2026-08-06:

| requirement | status | notes |
|---|---|---|
| `client_order_id` | **available** | present on every order object; use it |
| maker/taker flag per fill | **available** | `is_taker` on `/portfolio/fills` |
| per-fill fee | **available** | `fee_cost` |
| public tape with aggressor | **available** | `/markets/trades` → `taker_side`, `taker_book_side`, `taker_outcome_side`, `count_fp`, `created_time` |
| order book | **L2 only** | `/markets/{t}/orderbook` returns `[price, aggregate_size]` per level |
| **exchange-reported queue position** | **DOES NOT EXIST** | Kalshi never emits L3. No queue field on any endpoint, for anyone |

**§3 as originally written is not implementable.** There is no queue position to
read. Do not spend time looking for it — the runner's own header has said so
since it was written.

**What replaces it — and it is better than displayed size.** We join the back of
the queue at a known price `P` at a known timestamp. From that moment, the
public tape tells us exactly how much volume trades *at* `P` on our side. So:

- if we fill after `V` contracts have traded at `P`, our true queue position was **≤ V**
- if we cancel unfilled after `V` traded, our true queue position was **> V**

That is a **censored observation of true queue position** on every single order —
left-censored on fills, right-censored on cancels. It is measured, not assumed,
and it is exactly the input a survival model needs to estimate
`P(fill | queue, state, action)`. Displayed size at submission is retained as a
covariate (an upper bound on queue ahead), never as the queue itself.

## 1. Every opportunity — `opportunities.parquet`

One row per market that satisfies **base eligibility**, whether or not we act.
Skipped observations are the control group; losing them makes the whole dataset
unusable for policy estimation.

```
opportunity_id          uuid, primary key
ts_local_ms             int64    local clock at evaluation
ts_exchange_ms          int64    exchange clock (from the market/orderbook payload)
ticker                  str
coin                    str
event_ticker            str
window_open_ms          int64
window_close_ms         int64    derived from the wkey (ET ticker clock + UTC offset), NOT expected_expiration_time
secs_remaining          float64
favourite_side          str      "yes" | "no"
yes_bid, yes_ask        float64
no_bid,  no_ask         float64
spread_ticks            int32
tick_size               float64  varies by price: 0.001 below 10c and above 90c, else 0.01
book_bid_levels         list<struct<price:float64, size:float64>>   full depth
book_ask_levels         list<struct<price:float64, size:float64>>
displayed_qty_at_our_px float64  size at the level we would join
cum_volume              float64  volume_fp
recent_trades           list<struct<ts_ms:int64, price:float64, size:float64, taker_side:str>>
underlying_a0           float64  floor_strike
underlying_last         float64  best available index reference
feature_*               float64  EVERY feature the strategy computes, one column each
filter_*                bool     EVERY filter result, one column each, before short-circuiting
eligible                bool
skipped                 bool
skip_reason             str      null when acted on
strategy_version        str
git_commit              str
```

**Two rules.** Evaluate and record *all* filters, not just up to the first
failure — otherwise the reasons are censored by evaluation order. And write the
row before any submission attempt, so a crash cannot lose the observation.

## 2. Every submitted order — `orders.parquet`

```
client_order_id     str, generated by us, primary key, persisted BEFORE submission
order_id            str, exchange-assigned, null until acknowledged
opportunity_id      uuid, foreign key
ticker, side, action, price, quantity
ts_submit_ms        int64
ts_ack_ms           int64
ack_latency_ms      int64
accepted            bool
post_only_honoured  bool
reject_reason       str
reserved_capital    float64
strategy_version    str
git_commit          str
treatment           str    see §7
```

**Never mutate internal state before the exchange confirms acceptance.** The
existing runner increments deployed capital optimistically; that is how the
`resting` double-count bug happened. Generate `client_order_id`, persist the
intent, submit, and only update exposure on a confirmed ack.

## 3. Queue — `queue_snapshots.parquet`

Not exchange-reported (see §0). Reconstructed by differencing the public tape.

```
client_order_id         str
ts_ms                   int64
displayed_ahead_at_post  float64   size at our price when we joined (upper bound)
cum_traded_at_our_px    float64   volume traded AT our price since submission, our side
cum_traded_all_px       float64   total volume in the market since submission
book_size_at_our_px     float64   current displayed size at our level
inferred_ahead_lower    float64   0 if filled, else cum_traded_at_our_px
inferred_ahead_upper    float64   cum_traded_at_our_px if filled, else +inf
event                   str       "periodic" | "pre_fill" | "pre_cancel" | "at_expiry"
```

Snapshot at least every 5 s while resting, and always immediately before a
fill, before a cancel, and at expiry. `inferred_ahead_lower/upper` is the
censored interval — feed it to a survival model, not to a point estimate.

## 4. Order lifecycle — `order_events.parquet`

```
client_order_id, order_id, ts_ms
state       str    accepted|resting|partial_fill|filled|cancel_requested|cancel_confirmed|expired|rejected
detail      str
filled_qty_cum, remaining_qty  float64
```

Append-only. Every transition, including ones observed only after a restart.
Nothing may disappear across restarts — reconcile from
`/portfolio/orders` on startup and emit synthetic events for anything missed.

## 7. Randomised execution experiment — `assignments.parquet`

After an opportunity passes the **frozen** eligibility rule, assign exactly one
treatment. Assignment is generated **before** submission and persisted, so it
survives restarts and cannot be reconstructed after the fact.

| treatment | action |
|---|---|
| A | shadow only — evaluate, never submit |
| B | join best bid (current behaviour, the control) |
| C | one tick less aggressive |
| D | improve by one tick (only when spread permits) |
| E | early cancellation |
| F | standard cancellation |
| G | quantity 1 |
| H | quantity 2 |

```
opportunity_id, treatment, assigned_ts_ms, rng_seed, rng_stream_position, frozen_rule_version
```

Use a counter-based RNG keyed on `opportunity_id` so assignment is reproducible
and restart-safe. Treatment A is what makes the rest identifiable: it is the
only arm that observes the counterfactual without touching the book.

## 8. What to estimate

Replace every fixed assumption with a conditional estimate:

```
P(fill | outcome, state, action)

state  = queue interval, spread, price, secs_remaining, cum_volume, coin, quantity
action = price offset, quantity, cancellation policy
```

Fit as a **survival model with censoring** (the queue observations in §3 are
interval-censored), not a logistic on fill/no-fill — a cancelled order is not a
"no fill", it is an observation truncated at the cancel time.

## 9. Objective

Not edge per fill. **Expected value per submitted order**, and ultimately per
*eligible opportunity*:

```
V(X, A) = E[ pnl | state X, execution policy A ]
```

Optimise `A` directly. Edge per fill is exactly the metric that made
quote-improvement look attractive when it was not: every filter tested in this
repo raises edge-per-fill and lowers dollars.

## 10. Repository layout

```
capture/
  opportunities.parquet     orders.parquet          order_events.parquet
  assignments.parquet       queue_snapshots.parquet book_snapshots.parquet
  public_trades.parquet     fills.parquet           positions.parquet
  settlements.parquet       account_snapshots.parquet
  strategy_versions.parquet manifest.json
```

Partition by UTC date. `manifest.json` records schema version, git commit,
row counts and time bounds per file so a reader can detect gaps.

## 11. Production changes required

1. State changes **only** after confirmed acceptance
2. Startup **reconciles exchange state before trading** — never assume flat
3. Persistent `client_order_id` on every order (the field exists; use it)
4. Exposure read from exchange state, never reconstructed
5. Full pagination everywhere (`cursor` until exhausted)
6. Duplicate runners impossible — OS-level lock file with pid + liveness check
7. Watchdog can cancel orders directly, not only kill the process
8. Every restart reconstructs resting orders from `/portfolio/orders`

## 12. Success criteria

Optimise: P&L per eligible opportunity, per submitted order, per submitted
contract, per filled contract; fill probability conditional on state; queue
dynamics; partial-fill behaviour; capital efficiency.

**Not** historical win rate.

## Why this matters — what the current data cannot answer

The 73-day reconstruction in this repo established that no *selection* filter
beats keep-all, even chosen with hindsight (see README §4). Every cut raises
edge-per-contract and loses dollars. That result is solid and it closes the
selection question.

What it cannot answer is the **execution** question, because execution was
modelled rather than measured. The one measured execution fact —
`fill|LOSE = 1.0000` at every posting price while `fill|WIN = 0.856` — implies
the entire remaining loss is queue-driven adverse selection. Whether that is
attackable is unknown, and unknowable without §3 and §7.

That is the whole reason for this specification.
